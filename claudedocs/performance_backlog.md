   주장은 P@1 로 안 잡힌다.

   결정적 검사(재현 가능, 주축) + agent-as-judge(주관 축, `--judge`)로 나눴다.
   판정자 점수는 모델이 바뀌면 흔들리므로 결정적 검사와 분리해 보고한다.

   **첫 기준선(미해결 8건)**: 섹션 완결률 **1.0**(7/7) · 근거 사용률 **1.0** ·
   구체성 평균 16.1 · 분량 평균 3,951자 · 한자 혼입 **0** · **환각 인용 2건**.

   찾은 결함 — 스트리밍 경로가 본문의 환각 인용을 사용자에게 알리지 않았다.
   구조화 경로(`_llm_explain`)는 `dropped` 를 주는데, 실제 UI 가 쓰는 스트리밍
   경로는 `citations` 를 교집합으로만 계산하고 본문이 언급한 **미제공 사례는
   조용히 넘겼다**. 이제 `done` 이벤트에 `dropped` 를 실어 화면이 경고한다
   (실측: LSI-112 본문이 LSI-133·LSI-70 을 언급 → 경고 표시 확인).

   **2차(판정자 축)** — 근거 충실도 8.5 / 실행 가능성 8.5 였는데, 지적된 "근거 없는
   주장" 6건이 **날조가 아니라 일반 도메인 지식**(BKOPS 정의·NFC 동작 원리)이었다.
   문제는 엔지니어가 **어디까지가 검증된 사례이고 어디부터가 모델의 일반 지식인지
   구분할 수 없다**는 것이다 — 사례 근거는 실제 해결된 이슈에서 왔지만 일반 지식은
   이 칩·FW 에서 틀릴 수 있다.

   프롬프트에 구분 규약을 넣었다: 사례 확인 → 인라인 인용, 배경 설명 → `(배경)`,
   추정 → `(추정)`. 결과:

   | | 라벨 전 | 라벨 후 |
   |---|---|---|
   | 판정 근거충실도 | 8.5 | **9.0** |
   | 판정 실행가능성 | 8.5 | **9.5** |
   | 표시 없는 근거 없는 주장 | 6건 | **3건** |
   | 배경/추정 표시 | 0 | 3.2 / 4.5 per 분석 |

   중간에 **판정자가 새 규약을 몰라 점수가 거꾸로 갔다**(8.5→7.25, 지적 6→12) —
   표시된 배경까지 위반으로 셌기 때문이다. 투명하게 표시할수록 점수가 깎이는
   역설이라, 판정 기준을 제품 규약에 맞춰 정렬한 뒤에야 실제 개선이 보였다.
   **측정 기준은 제품과 함께 진화해야 한다.**
   (n=6 이라 판정 점수는 흔들릴 수 있다 — 결정적 검사가 주축인 이유다.)

   **계측 자체를 두 번 고쳤다** — 처음엔 한자 판정을 직접 만들어 한글 음절까지 잡아
   8/8 건이 "한자 혼입" 으로 오보됐고, 인용 정규식에 `\w` 를 써서 조사가 붙은
   "LSI-157은" 이 환각으로 잡혔다. 또 큐레이션 키(`LSI-7-rca`)와 질의 자신의 키를
   허용 집합에 넣지 않아 정상 인용이 환각으로 셌다. 계측이 거짓말하면 없는 결함을
   고치게 된다 — `lang_validator.find_violations` 를 재사용해 단일 소스로 맞췄다.

13. **[P2] 인용 위반 시 재생성 경로 없음** — 항목 5의 잔여.
    현재는 환각 키를 `dropped`로 떼어낼 뿐 본문의 잘못된 인용 문장은 남는다.
    → 검증 실패 시 1회 재생성, 그래도 실패면 템플릿 fallback.

14. **[완료 2026-08-02] 서빙 지연 상설 계측** — `GET /metrics`.
    **2차(2026-08-02)**: 가장 비싼 경로인 심층 분석이 빠져 있어 추가했다.
    실측 대비가 캐시의 가치를 그대로 보여 준다 — **생성 p50 54초 vs 캐시 히트 0.0ms**.

## G. 자기개선 루프 검증 (2026-08-02)

### G-1. **승격 제안은 검색을 개선하지 않는다 — 지식 정리 효과다**

큐에 쌓인 제안 53건 중 **51건이 `promote_known_issue`** 였다. "중복 사례를 정리하면
검색이 좋아진다" 는 가정이 맞는지 전후로 쟀다(임시 저장소에 승격 후 원복).

| | 승격 전 | 승격 후 3건 |
|---|---|---|
| confusable P@1 / 게이트 | 1.000 / 1.000 | **1.000 / 1.000** |
| paraphrase P@1 / 게이트 | 1.000 / 1.000 | **1.000 / 1.000** |
| known_issue 주석이 붙은 매치 | 1/48 | **9/48** |

**검색은 그대로**이고, 바뀌는 것은 매치에 붙는 "알려진 고장모드" 주석이다. 즉 이
제안의 값어치는 검색 개선이 아니라 **읽는 사람이 중복임을 알게 되는 것**이다.
rationale 에 그대로 적어 우선순위를 오해하지 않게 했고, P2 → **P3** 으로 내렸다.

한계: 검색 지표가 이미 1.0 이라 **작은 개선은 이 측정으로 보이지 않는다.** "개선이
없다" 가 아니라 "이 해상도로는 안 보인다" 가 정확하다.

### G-2. **큐가 한 유형으로 덮여 있었다 — 53건 → 7건**

군집마다 한 건씩 뽑아 51건이 쌓였다. 사람이 처리하는 목록인데 한 종류가 화면을
덮으면 다른 유형(모순·온톨로지)이 묻히고, 결국 아무도 큐를 보지 않게 된다.
상위 5건(큰 군집 우선)만 개별 제안으로 올리고 나머지는 묶음 안내 1건으로 대체했다
— "승격 대상 군집이 30개 더 있다. 대시보드의 '중복 지식' 카드에서 한 번에 본다."

### G-3. **큐가 단조 증가했다 — 고친 것이 사용자에게 전달되지 않았다**

G-2 에서 생성 규칙을 고쳐 제안을 53건 → 7건으로 줄였는데, **저장된 큐는 그대로
53건이었다.** `sync()` 가 추가만 하고 회수하지 않아, 근거를 잃은 제안(사례가 이미
승격됨·군집이 흩어짐·규칙이 바뀜)이 영원히 남는 구조였다. 코드는 고쳤지만 사람이
보는 화면은 하나도 바뀌지 않은 상태였다 — 고쳤다고 보고했으면 거짓이 될 뻔했다.

`sync(generated, prune=True)`: 이번 생성분에 없는 open 제안을 **superseded** 로 회수.

| | 전 | 후 |
|---|---|---|
| open | 53 | **8** |
| superseded | 0 | 46 |

지우지 않고 상태로 남긴 이유는 "왜 사라졌나" 를 추적할 수 있어야 하기 때문이다.
회수로 드러난 것: 51건 밑에 묻혀 있던 **`resolve_contradiction` P2 한 건** — 큐에서
유일하게 P2 인 제안이 이제 맨 위에 있다. 큐 정리의 값어치가 그대로 보인다.

안전장치(`tests/test_improve_queue.py` 로 고정):
- 사람의 결정(done/dismissed)은 회수 대상이 아니고 다시 생성돼도 open 으로 안 돌아온다
- **생성이 통째로 실패해 빈 목록이면 회수하지 않는다** — 실패가 큐를 쓸어버리면 안 된다
- `prune=False` 로 부분 생성 결과에서 회수를 끌 수 있다
- id 는 `len(items)+1` 대신 최대 일련번호 +1 — 항목이 빠져도 겹치지 않는다

### G-4. **지식 공백 기록이 게이트 한 곳에만 붙어 있었다**

`data/knowledge_gaps.json` 이 0건이라 죽은 코드를 의심했다(실제로 embed_cos 게이트가
그런 식으로 죽어 있었다). **먼저 죽었는지 재료가 없는지를 갈랐다** — 무관 질의 3건을
`/recommend` 에 넣으니 3건 모두 기록됐다. 코드는 살아 있다.

0건인 이유는 **실사용 질의가 전부 KB 안의 이슈**라 게이트가 걸릴 일이 없어서다.
미해결 이슈 30건으로 `/rca/draft` 를 돌려도 게이트 미통과 0건(26건 큐잉·4건 기승인).

다만 기록이 `/recommend` **한 곳에만** 붙어 있었다. 정작 신호가 가장 센 자리 —
사용자가 자동 RCA 를 요청했다가 "사례 없음" 으로 거절당하는 순간 — 은 남지 않았다.
게이트가 막는 자리마다 `_record_gap()` 을 부르도록 바꾸고 사유를 나눴다:

| 사유 | 자리 |
|---|---|
| `no_coverage` | `/recommend` — 검색이 막힘 |
| `rca_refused` | `/rca/draft` — 자동 RCA 거절 (**신호 가장 강함**) |
| `explain_no_coverage` | `/recommend/explain/cached` — MCP 클라이언트 직접 호출 |

**부르지 않는 곳: 예열 배치.** 사람이 물어본 게 아니라 KB 전량 훑기라, 기록하면
전체가 공백으로 들어와 "자주 묻는 영역" 신호를 덮는다. 테스트로 고정했다.

순간 중복 접기(`RVP_GAPS_DEDUP_SEC`, 기본 60초) — 빈도 집계가 목적인데 새로고침·
재시도가 같은 사건을 여러 번 세면 "자주 묻는다" 가 "여러 번 눌렀다" 로 오염된다.

배선은 인위적으로 게이트를 막아 확인했다(무관 내용의 미해결 이슈 주입 →
`reason_code=no_coverage`, `rca_refused` 1건 기록). **실트래픽에서는 아직 0건이다** —
지금 값어치는 관측 준비이지 측정된 개선이 아니다. E-5("공백을 무관 셋으로 승격")는
재료가 쌓일 때까지 여전히 막혀 있다.

## H. 운영 결함 (2026-08-02, 서버 재기동 중 발견)

### H-1. **서버 모듈이 두 번 적재되고 있었다**

`python backend/server.py` → 파일이 `__main__` 으로 한 번 실행되고, 그 안의
`uvicorn.run("server:app")` 이 같은 파일을 `server` 모듈로 **다시 import** 한다.
모듈 본문이 두 번 도니 MCP 앱과 FastAPI 앱이 두 벌씩 만들어졌다. 로그의
`[mcp] 마운트됨` 이 두 번 찍혀 드러났다 — 트래픽은 한쪽만 받으니 나머지는 사장된다.

다행히 예열·Jira 폴러는 `_lifespan` 안이라 중복 실행되지 않았다(둘 다 돌았다면
LLM 비용이 두 배였다). 지금 피해는 메모리 낭비지만, **모듈 수준에 부작용이 하나라도
생기면 조용히 두 번 실행된다** — 파일 쓰기, 스레드, 외부 등록 무엇이든.

`uvicorn.run(app, ...)` 으로 객체를 넘겨 해결. reload 를 쓰지 않으므로 문자열일 이유가 없다.
확인: 마운트 로그 2회 → **1회**.

### H-2. **슬래시 없는 `/mcp` 가 405 였다**

`app.mount("/mcp", ...)` 는 POST 를 자동 리다이렉트하지 않는다. README 본문은
`/mcp` 로 안내하고 설정 예시만 `/mcp/` 였다. 문서대로 `https://<서버>/mcp` 를 넣은
클라이언트는 **405 만 보고 이유를 알 수 없다** — 슬래시 하나로 나는 실패는
디버깅하기 최악이다.

307 리다이렉트를 추가했다(301/302 는 POST 를 GET 으로 바꿔 본문이 사라진다).
네트워크 경로로 실제 `initialize` 를 던져 양쪽 다 `serverInfo` 가 오는 것을 확인했고,
테스트로 고정했다. 인프로세스 테스트만 있어서 이 결함을 놓쳤다 — 마운트 문제는
**네트워크 경로로 찔러야** 보인다.

부수 확인: MCP 의 Host 검증(DNS rebinding 방어)이 TestClient 기본 호스트
`testserver` 를 421 로 막는다. 방어는 의도대로 동작 중 — 테스트가 준수하도록 고쳤다.

### H-3. **인프로세스 테스트만으로는 안 보이는 층이 있다**

H-2 를 놓친 이유가 구조적이다 — 테스트 8종이 전부 인프로세스(TestClient/
ASGITransport)다. 마운트·정적 서빙·리다이렉트·**기동 자체**는 실제 소켓으로 찔러야
보인다. `tests/test_http_smoke.py` 를 추가했다: `python backend/server.py` 로
프로세스를 띄우고(Dockerfile 의 CMD 와 동일) 빈 포트에 바인드해 네트워크로 훑는다.
LLM·Jira 는 끈다.

**테스트가 실제로 그 회귀를 잡는지 확인했다** — 통과하는 테스트는 증거가 아니다:

| 되돌린 결함 | 결과 |
|---|---|
| `uvicorn.run("server:app")` (이중 적재) | ✗ 모듈은 한 번만 적재된다 — '마운트됨' 2회 |
| 307 리다이렉트 제거 | ✗ 슬래시 없는 /mcp 는 307 — 405 |

확인 항목: 기동·단일 적재·미인증 401·로그인 후 200·API 라우트가 SPA 폴백에 먹히지
않는지·MCP 가 `/mcp` 와 `/mcp/` 양쪽으로 붙는지.

### H-4. **자기개선 루프가 운영과 다른 임베딩으로 KB 를 보고 있었다**

브라우저로 대시보드를 열어 보다 두 카드가 **서로 모순되는 것**을 발견했다:

  · "지식 모순" 카드 → ✓ 모순 없음
  · "개선 큐" → `resolve_contradiction` **P2** (LSI-210|LSI-211, doc 0.877 / rc 0.462)

같은 `contradictions.detect()`, 같은 임계값(0.85/0.60)인데 결론이 갈렸다. 원인은
**유사도 공간이 달랐다**: 서버는 `embed_backend/embed_model` 을 환경변수에서 넘겨
bge-m3(API)를 쓰는데, `self_improve._build_recommender()` 는 그 인자를 넘기지 않아
Recommender 기본값인 **로컬 MiniLM** 으로 떨어졌다.

즉 군집·모순·온톨로지 제안 전부가 **사용자가 실제로 검색하는 공간이 아닌 곳**에서
계산되고 있었다. 없는 문제를 만들고, 있는 문제를 놓쳤다.

`_eval_with()` 도 같은 결함이었다 — L2 파라미터(gate_cos 등) 튜닝까지 다른 공간에서
평가했다. 두 곳을 `embed_kwargs()` 하나로 묶었다. E-0 에서 "격리 벤치로 서버 지연을
예측하지 말 것" 을 배웠는데, 같은 함정의 정확도 판이었다.

검증: 오프라인 탐지 1건 → **0건**, 서버 0건과 일치. 큐 재생성 시 거짓 모순 S-22 는
H-1 의 회수 기능으로 자동 철회됐다(open 8 → 6, superseded 46 → 49). 브라우저로
대시보드를 다시 열어 두 카드가 일치하는 것까지 확인했다.

부수 확인 — **군집 임계값 0.80 은 재보정이 필요 없다.** bge-m3 공간에서 쌍 유사도는
p95 가 0.691 인데 ≥0.80 과 ≥0.90 이 똑같이 236쌍이다. 즉 0.70~0.90 사이가 비어 있어
그 구간 어디를 잡아도 결과가 같다. 임계값이 골짜기에 놓여 둔감하다.

### H-5. **임베딩 기본값을 클래스가 아니라 환경에서 읽는다**

H-4 를 호출부마다 `env_embed_kwargs()` 를 넘기는 식으로 고쳤는데, 그건 **또 빠뜨릴 수
있는 구조**다. 실제로 감사해 보니 `scripts/build_eval_confusable.py` 도 빠져 있었다 —
**변별 평가셋의 혼동 후보가 MiniLM 공간에서 골라지고 있었다.**

근본 해결: `Recommender.embed_model/embed_backend` 기본값을 `""`/`"fastembed"` 에서
**`None`** 으로 바꾸고, `__post_init__` 이 미지정일 때 환경변수를 읽는다.

| 상황 | 결과 |
|---|---|
| 환경변수 있음, 인자 없음 | **openrouter / bge-m3** (운영과 동일) |
| 인자 명시 | 그대로 (모델 비교 A/B 를 위해) |
| 환경변수 없음 (테스트·오프라인) | fastembed / MiniLM — 폴백은 유지 |

폴백 자체는 남겼다(키·네트워크 없이 도는 테스트가 있다). 대신 **조용하지 않게** 했다 —
임베딩 초기화 실패 시 "이 인스턴스의 검색 결과는 운영과 다르다, 평가·튜닝 수치로 쓰지
말 것" 을 같이 찍는다. 두 번의 사고 모두 *조용한* 폴백 때문이었다.

### H-6. **평가셋을 바로잡으니 폴백 게이트가 처음으로 변별됐다**

`data/eval_confusable.json` 을 bge-m3 공간에서 재생성(재서술 25건 포함):

**34건 중 20건(59%)의 혼동 후보가 바뀌었다** — 그동안 다른 문제를 풀고 있었다.
후보 유사도 중앙 0.740 → 0.698.

바로잡은 셋으로 측정:

| 구성 | P@1 | 게이트 | 무관차단 |
|---|---|---|---|
| **운영(hybrid_embed + rerank)** | **1.000** | **1.000** | 1.000 |
| rerank OFF (embed_cos 폴백 게이트) | 0.853 | **0.735** | 1.000 |

## I. 프론트엔드 접근성·사용성 (2026-08-02, 브라우저 실측)

측정은 클래스 이름을 훑는 대신 **브라우저에서 실제 렌더링을 재서** 했다.
대비(WCAG)는 **위반 0건** — 앞선 다크 테마 작업이 유효하다. 모바일은 범위에서 제외.

### I-1. **이슈 목록 137개가 통째로 탭 순서를 막고 있었다**

키보드로 가운데 본문(추천 결과)에 닿으려면 **Tab 을 273번** 눌러야 했다.

표준 listbox 규약(roving tabindex)으로 바꿨다 — 선택된 행만 `tabIndex=0`, 나머지는
`-1`. 목록 안 이동은 **이미 있던 ↑/↓** 가 맡는다(기능을 새로 만든 게 아니라
탭 순서에서 뺀 것이다).

| | 전 | 후 |
|---|---|---|
| 전체 탭 정지점 | 278 | **26** |
| 가운데 본문까지 Tab | 273 | **21** (바로가기 사용 시 **1**) |

주의한 것: roving tabindex 는 **선택이 바뀔 때 포커스도 옮겨야** 한다. 안 그러면
방금 `tabIndex=-1` 이 된 항목에 포커스가 남아 다음 Tab 이 문서 처음으로 튄다.
↑/↓ 로 옮길 때만 따라가고 **마우스 클릭은 포커스를 뺏지 않는다**(입력 흐름 방해).
브라우저에서 ↑/↓ 2회 → 포커스가 선택 행과 일치, 클릭 → `tabIndex=0` 이 선택 행으로
이동하는 것까지 확인했다.

### I-2. 본문 바로가기 · 문서 언어 · 상태 알림

- **본문 바로가기**: 첫 Tab 에 나타나고 Enter 로 `#main-content` 에 **실제 포커스가
  옮겨간다**(`tabIndex={-1}` 없이는 스크롤만 되고 탭 순서는 링크 자리에 남는다).
- **`<html lang>` en → ko**: 화면은 전부 한국어인데 en 이었다. 스크린리더가 영어 음성
  규칙으로 읽고 브라우저 번역·글꼴 대체도 틀어진다.
- **상태 알림(`role=status` `aria-live=polite`)**: 라이브 영역이 **0개**였다. 버튼을
  누르고 수 초 뒤 결과가 오는데 화면을 보지 않는 사용자에겐 아무 일도 없는 것과
  같았다. 검색 중·생성 중·N건 찾음·사례 없음·오류를 알린다. 실측으로 "유사 사례
  4건을 찾았습니다" 가 들어가는 것을 확인했다.

### I-3. 남아 있던 라이트 패널 · 작은 클릭 영역

- 게이트 미통과 안내가 `bg-amber-50 / text-amber-800` — 다크 UI 에서 이 블록만
  하얗게 떴다. 위쪽 오류 패널과 같은 `amber-950/40` 규칙으로 맞췄다.
- 패널 접기 `◀ ▶` 가 **22×16px** — 마우스로도 집기 어려웠다. 28×28 로 넓히고
  `aria-label` 을 붙였다(기호만으로는 무엇을 접는지 알 수 없다).

**계측 주의**: `button:not([disabled])` 로 세면 `tabindex="-1"` 인 버튼까지 잡혀
"개선 없음(278)" 으로 보였다. 탭 정지점을 셀 때는 `tabindex="-1"` 과 숨은 요소를

## E-6. 폴백 게이트 재보정 — **임계는 최적, 손실은 다른 원인** (2026-08-02)

`scripts/calibrate_gate_cos.py` 신설. 정답 171 / 무관 66(교정된 평가셋 4종),

### 결론: **0.57 은 이미 최적이고 움직일 자리가 없다**

무관 최대 코사인이 **0.563** — 0.57 은 무관을 전부 막는 **최저** 임계다.

| 임계 | 이슈 선택(통과/차단) | 자유 문장(통과/차단) |
|---|---|---|
| 0.55 | 1.000 / 0.955 | 0.965 / 0.955 |
| **0.57** | **1.000 / 1.000** | **0.947 / 1.000** |
| 0.60 | 0.971 / 1.000 | 0.901 / 1.000 |

### 26.5% 의 정체 — 경로를 나눠 재야 보인다

앞선 "26.5% 차단" 은 **confusable 셋 · 자유 문장**에만 있었다. 경로를 섞으면 안 된다:

| 경로 | 정답 통과 |
|---|---|
| 이슈 선택(chip·category 있음) | **1.000** (4종 모두) |
| 자유 문장(메타 없음) | 0.947 — confusable 만 0.735, 나머지 3종 1.000 |

막히는 9건은 전부 confusable(기술용어를 뺀 현장 말투 재서술)이고 코사인 0.498~0.561 이
무관 최대 0.563 과 **겹친다.** 어떤 임계로도 못 가른다 — 임계 문제가 아니다.

### BM25 3번째 신호는 재보고 **버렸다**

무관 최대 6.76 vs 구제 대상 7.67 — 여유 **13%** 뿐. BM25 원점수는 정규화가 없어 KB 가
커지면 IDF 와 함께 흔들려 고정 임계가 조용히 무너진다. z-점수 정규화는 **더 나빴다**
(여유 **-71%**: 무관도 코퍼스가 평평하면 z 가 높다 — 내 가설이 틀렸다).
결정적으로 이건 **폴백** 게이트라 두 실패의 값이 다르다: 막으면 "사례 없음"(안전),
통과시키면 무관 사례에 근거한 환각 근본원인(위험). 얇은 여유로 위험한 쪽을 늘릴 이유가 없다.

### 대신 고친 것 — 열화가 **영구화되고 보이지 않던** 문제

임계를 재다 더 큰 결함을 찾았다.

1. **차단기가 영영 닫히지 않았다.** 열리면 `rerank=False` 가 되어 KB 를 다시 만들
   때까지 그대로였다 — 게이트웨이가 5분 끊긴 것만으로 그날 내내 약한 게이트로 돌았다.
   → `rerank_retry_sec`(기본 300초) 후 한 번 재시도. 성공하면 복구, 실패하면 즉시
   재차단(대기당 재시도 1회 — 요청 폭주 없음).

2. **열화가 지표에서 사라졌다.** 차단기가 열리면 재순위를 시도하지 않으니 실패가
   기록되지 않고, 링버퍼(500)가 밀려나면 `rerank_failures` 가 **0** 이 된다.
   문제가 영구화되는 순간 지표가 사라지는 셈이다.
   → `/metrics` 에 `rerank: {enabled, degraded, consecutive_fails, tripped_at, gate}` 를
   **살아 있는 추천기에서** 읽어 노출.

`tests/test_rerank_breaker.py` 로 고정(네트워크 없이 가짜 리랭커): 한계 도달 시 차단 ·
닫힌 동안 호출 안 함 · 대기 후 복구 · 카운터 초기화 · 계속 실패하면 재차단(대기당 1회) ·
`retry_sec=0` 이면 복구 안 함 · `/metrics` 가 열화를 즉시 보여줌.

| mpnet-base @local | **13ms** | 0.396 | 0.500 | **불가 — 겹침(-0.105)** |
| **e5-large @local** | 64~348ms | 0.862 | 0.844 | **가능 (+0.018)** |

**mpnet 은 함정이다.** rerank 를 켜고 평가하면 전 지표 1.0 으로 보이지만, 그것은
rerank 게이트가 판정했기 때문이다. embed_cos 단독으로는 무관 질의 40건 중 4건이
통과하고 정답 4건이 차단된다(t=0.48). 폴백이 필요한 순간에 못 쓰는 폴백이다.
→ **평가에서 rerank 를 끈 경로도 반드시 함께 본다**(E-5 의 변별력 문제와 같은 뿌리).

**e5-large @local 채택 후보** (임계 0.853, e5 는 query:/passage: 프리픽스 필요 —
코드에 이미 있음):
  · rerank ON(기본): paraphrase/generated P@1·게이트·무관차단 **전부 1.000**
  · rerank OFF(폴백): 게이트 통과 **1.000** · 무관 차단 **1.000** (P@1 0.898 —
    순위는 rerank 없이 조금 낮지만, 폴백에서 중요한 것은 게이트다)
  · `/recommend` 전체 중앙 **673ms → 365ms (-46%)**, 임베딩 API 의존 제거
  · 주의: 질의 지연이 64~348ms 로 흔들린다(CPU 연산). 모델 로드 4.4s 는 프로세스당
    1회 — 기동 워밍업이 필요하다. 마진 +0.018 은 여전히 얇아 모델·KB 변경 시 재보정.

**더 줄이려면** E-1 의 "게으른 계산" 을 e5-large 위에 얹는다 — 정상 경로는 임베딩
0회, rerank 실패 회차에만 로컬로 계산해 게이트를 세운다. 게이트(안전장치)는 지키고
매치 카드의 embed_cos 표시만 정상 경로에서 잃는다.

### E-1. **[구현·기본 비활성 2026-08-02] 게으른 임베딩 — 280ms 대신 정확도 1건**

구현했고 **기본은 끈다**(`RVP_LAZY_EMBED=1` 로 켠다). 이유는 측정 결과다.

| 구성 | total p50 | rank | rerank | confusable P@1 | paraphrase P@1 |
|---|---|---|---|---|---|
| **현행 (기본)** | 642ms | 317 | 324 | **1.000** | 1.000 |
| lazy + top_n 30 | **363ms** | 4.9 | 358 | **0.971** | 1.000 |
| lazy + top_n 20 | — | — | — | 0.971 | 0.980 |

**변별 셋이 없었으면 채택했을 것이다.** 포화된 셋(paraphrase·generated)에서는 세
구성이 전부 1.000 으로 같아 보였고, 실제로 이번 세션 초반에 그 근거로 "품질 동일,
-53%" 라고 제안했었다. eval_confusable 을 만든 뒤에야 34건 중 1건을 잃는다는 것이
드러났다 — E-5 가 값을 한 순간이다.

**판단**: 채택하지 않는다.
  · 이 도구의 가치는 근본원인을 맞히는 것이다. 잘못 짚으면 엔지니어가 며칠을 잃는다.
  · 280ms 는 사용자가 뒤이어 여러 문단의 분석을 읽는 흐름에서 체감되지 않고,
    심층 분석 자체는 이미 캐시로 0.01초다.
  · 정상 경로에서 `embed_cos` 표시도 사라진다(사용자가 필요하다고 확인한 신호).
높은 QPS·지연 민감 배포에서는 켤 수 있도록 스위치는 남겼다.

발상: rerank(cross-encoder)가 상위 후보를 다시 채점하므로, 1차 랭커의 역할은
**정답을 top-N 안에 넣는 것(recall)** 뿐이다. 정렬 품질은 rerank 가 만든다.
그렇다면 1차에서 임베딩(질의당 API 왕복)을 쓸 이유가 없다.

recall 실측(paraphrase+generated 73건):

| 1차 랭커 | recall@5 | @10 | @20 | @30 | 빌드 |
|---|---|---|---|---|---|
| `hybrid_embed` (현행) | .986 | 1.000 | 1.000 | 1.000 | 4,449ms |
| `hybrid` (bm25+graph) | .932 | .959 | **.986** | **1.000** | 24ms |
| `bm25` 단독 | .932 | .959 | .986 | 1.000 | 15ms |

→ 임베딩을 빼면 top-20 에서 1건(73건 중) 놓치지만 **top-30 에서는 전부 회수**된다.

최종 품질·지연 실측:

| 구성 | paraphrase P@1 | generated P@1 | 게이트 | 무관차단 | 질의당 |
|---|---|---|---|---|---|
| A 현행 `hybrid_embed`+rerank20 | 1.000 | 1.000 | 1.000 | 1.000 | 734ms |
| B `hybrid`+rerank20 | 0.980 | 1.000 | 0.980 | 1.000 | 316ms |
| **C `hybrid`+rerank30** | **1.000** | **1.000** | **1.000** | **1.000** | **325ms** |

**rerank_top_n 을 20→30 으로 늘리는 비용은 +9ms**(같은 API 호출에 문서만 더 실림).

단, C 를 그냥 켜면 이득이 없다 — `recommend()` 의 신호 산출이 여전히 질의를
임베딩한다(운영 설정 실측: A 673ms/8회 → C 655ms/**8회** → 신호까지 끄면 316ms/**0회**).

**구현**: 질의 임베딩을 **게으르게** 만든다.
  · 1차 랭킹: bm25+graph (질의 임베딩 없음), `rerank_top_n=30`
  · 게이트: rerank 점수가 나왔으면 rerank 게이트만 쓴다(임베딩 불필요)
  · rerank 가 실패한 회차에만 질의를 임베딩해 embed_cos 게이트로 폴백
  → 정상 경로 임베딩 API **0회**, 기대 **673ms → 316ms (-53%)**

**감수할 것**: 정상 경로에서 매치별 `embed_cos` 표시가 사라진다(순위 근거는 rerank
관련도이므로 의미 손실은 작다). 대시보드의 클러스터·모순 분석은 KB 임베딩만 쓰므로
영향 없다.
