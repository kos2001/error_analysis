## E. 브레인스토밍 (2026-08-02 실측) — 남은 지연의 대부분은 "필요 없는 임베딩 호출"

### E-1. **[P1, 최대 효과] rerank 가 있으면 1차 검색에 임베딩이 필요 없다 — 673ms → 316ms**

발상: rerank(cross-encoder)가 상위 후보를 다시 채점하므로, 1차 랭커의 역할은
**정답을 top-N 안에 넣는 것(recall)** 뿐이다. 정렬 품질은 rerank 가 만든다.
그렇다면 1차에서 임베딩(질의당 API 왕복)을 쓸 이유가 없다.

recall 실측(paraphrase+generated 73건):

| 1차 랭커 | recall@5 | @10 | @20 | @30 | 빌드 |
|---|---|---|---|---|---|
| `hybrid_embed` (현행) | .986 | 1.000 | 1.000 | 1.000 | 4,449ms |
| `hybrid` (bm25+graph) | .932 | .959 | **.986** | **1.000** | 24ms |
| `bm25` 단독 | .932 | .959 | .986 | 1.000 | 15ms |

→ 임베딩을 빼면 top-20 에서 1건(73건 중) 놓치지만 **top-30 에서는 전부 회수**된다.

최종 품질·지연 실측:

| 구성 | paraphrase P@1 | generated P@1 | 게이트 | 무관차단 | 질의당 |
|---|---|---|---|---|---|
| A 현행 `hybrid_embed`+rerank20 | 1.000 | 1.000 | 1.000 | 1.000 | 734ms |
| B `hybrid`+rerank20 | 0.980 | 1.000 | 0.980 | 1.000 | 316ms |
| **C `hybrid`+rerank30** | **1.000** | **1.000** | **1.000** | **1.000** | **325ms** |

**rerank_top_n 을 20→30 으로 늘리는 비용은 +9ms**(같은 API 호출에 문서만 더 실림).

단, C 를 그냥 켜면 이득이 없다 — `recommend()` 의 신호 산출이 여전히 질의를
임베딩한다(운영 설정 실측: A 673ms/8회 → C 655ms/**8회** → 신호까지 끄면 316ms/**0회**).

**구현**: 질의 임베딩을 **게으르게** 만든다.
  · 1차 랭킹: bm25+graph (질의 임베딩 없음), `rerank_top_n=30`
  · 게이트: rerank 점수가 나왔으면 rerank 게이트만 쓴다(임베딩 불필요)
  · rerank 가 실패한 회차에만 질의를 임베딩해 embed_cos 게이트로 폴백
  → 정상 경로 임베딩 API **0회**, 기대 **673ms → 316ms (-53%)**

**감수할 것**: 정상 경로에서 매치별 `embed_cos` 표시가 사라진다(순위 근거는 rerank
관련도이므로 의미 손실은 작다). 대시보드의 클러스터·모순 분석은 KB 임베딩만 쓰므로
영향 없다.

### E-2. **[P2] HTTP 연결 재사용 — 호출당 68ms**

`recommender._openrouter_embed` 와 `reranker.rerank` 가 `requests.post` 를 직접
호출해 **매번 TLS 핸드셰이크를 다시 한다**. 실측(embeddings, n=6):
매 호출 새 연결 378ms(중앙) vs Session 재사용 311ms → **-68ms/호출**.
E-1 적용 후에는 호출이 rerank 1회뿐이므로 316ms → 약 248ms 를 기대한다.
모듈 수준 `requests.Session` 하나로 끝나는 변경이다.

### E-3. **[P2] KB 임베딩도 게으르게 — D-11 의 4.8초가 서빙 경로에서 사라진다**

E-1 을 적용하면 KB 임베딩은 (a) rerank 실패 시 폴백 게이트, (b) 대시보드의
클러스터·모순 분석에만 쓰인다. 둘 다 질의 경로가 아니다. 따라서 KB 임베딩 구성을
**첫 사용 시점까지 미루면** KB 가 바뀔 때마다 물던 4,787ms(D-11)가 사용자 질의에서
빠진다. D-11 의 증분 임베딩보다 먼저 할 수 있고 더 싸다.

### E-4. **[P2] 예열이 미해결 127건 중 20건만 덮는다**

`RVP_PREWARM_LIMIT` 기본 20 — 나머지 107건은 첫 클릭에서 여전히 수십 초를 기다린다.

생긴다. 다만 비용은 LLM 쪽이 지배적이므로, 전량 예열은 "야간 배치로 큐를 비우는"
형태가 맞다(질의 시각과 분리).

### E-5. **[P1, 측정 기반이 막혔다] 평가셋이 포화 — 개선을 볼 수 없다**

현재 4종 전부 P@1 1.0 이다. 즉 **지금부터의 품질 변화는 측정되지 않는다** — 좋아져도
나빠져도 1.0 이다. E-1 처럼 "품질 동일"을 주장하는 변경이 늘어나는데, 그 주장을
받쳐 줄 변별력이 없다는 것이 가장 큰 위험이다.

만들 것(난이도 순):
  · **혼동 후보를 심은 셋** — 같은 칩·같은 분류의 다른 고장모드를 정답 주변에 배치
  · **교차 칩 재서술** — 증상은 같고 칩만 다른 질의(칩 부스트가 과하게 먹는지 검출)
  · **다중 정답/부분 정답** — 현재는 단일 템플릿 정답만 인정
  · **부정 마이닝** — knowledge_gaps 에 쌓인 실제 미통과 질의를 무관 셋으로 승격
